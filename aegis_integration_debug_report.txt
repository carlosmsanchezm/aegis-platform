## 2. The Core Problem: TLS Certificate Mismatch

The `grpcurl` command to test the `CreateWorkspace` endpoint is failing with a `401 Unauthorized` error.

The root cause is a **TLS certificate validation failure** during the authentication process. The `platform-api` service, upon receiving a request, tries to verify the JWT by fetching the public keys (JWKS) from the Keycloak server. This internal, server-to-server connection fails because the name on the TLS certificate presented by Keycloak does not match the service name the `platform-api` is trying to connect to.

### 2.1. `grpcurl` Error Output

This is the error received by the client when attempting to call the `CreateWorkspace` endpoint.

```
ERROR:
  Code: Unauthenticated
  Message: unexpected HTTP status code received from server: 401 (Unauthorized); transport: received unexpected content-type "application/json"
```

### 2.2. `platform-api` Backend Logs

This is the critical log from the `platform-api` pod, which clearly shows the certificate validation error.

```json
{"level":"warn","ts":1762186869.4154718,"caller":"mw/auth.go:318","msg":"authentication failed","event":"auth_failure","reason":"token_parse","decision":"deny","source":"grpc","method":"/aegis.v1.AegisPlatform/ListWorkloads","source_ip":"10.244.1.108","error":"token is unverifiable: error while executing keyfunc: failed to fetch JWKS: Get \"https://aegis-services-keycloak-service.keycloak.svc.cluster.local:8443/realms/aegis/protocol/openid-connect/certs\": tls: failed to verify certificate: x509: certificate is valid for keycloak.localtest.me, aegis-services-keycloak.keycloak.svc.cluster.local, not aegis-services-keycloak-service.keycloak.svc.cluster.local"}
```

**Analysis of the Log:**
- **`platform-api` tries to connect to:** `https://aegis-services-keycloak-service.keycloak.svc.cluster.local:8443`
- **The certificate is only valid for:** `keycloak.localtest.me` and `aegis-services-keycloak.keycloak.svc.cluster.local`

The service name has an extra `-service` suffix that is not included in the certificate's list of valid names (Subject Alternative Names).

## 3. How the Mismatch Occurs (Helm Chart Investigation)

- The Keycloak service name is generated by the Keycloak Operator based on the `metadata.name` of the `Keycloak` custom resource.
- The `Keycloak` resource name is defined in `charts/aegis-services/templates/_helpers.tpl` as `aegis-services-keycloak`.
- The Keycloak Operator automatically appends `-service` to this name when creating the Kubernetes Service object, resulting in `aegis-services-keycloak-service`.
- However, the TLS certificate used by Keycloak was generated for the name `aegis-services-keycloak`, without the `-service` suffix.

This discrepancy is the source of the entire authentication failure.

## 5. Next Steps & Recommendation

The immediate blocker is the TLS certificate mismatch. The team needs to decide on the correct fix:

1.  **Option A (Recommended): Regenerate the Keycloak TLS Certificate.** The `keycloak-tls` secret should be recreated with a certificate that includes `aegis-services-keycloak-service.keycloak.svc.cluster.local` in its Subject Alternative Names (SANs). This is the most secure and correct long-term solution.

2.  **Option B (Workaround): Rename the Service.** Modify the Helm chart and/or the Keycloak Operator configuration to create the service with the name `aegis-services-keycloak` (without the `-service` suffix) to match the existing certificate. This may have downstream consequences if other components rely on the current service name.

Once the certificate and service name match, the `401 Unauthorized` error should be resolved, unblocking the rest of the integration work.
